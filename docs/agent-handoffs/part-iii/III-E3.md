- **Schema/API/contract change requested from another owner:** three gaps, all confirmed by reading `crates/tack-api/src/handlers/runner_admin.rs` directly (not just trusting III-E2's handoff, though it independently found gap 1):
  1. **No `GET /runners` (or per-runner) read endpoint.** `runner_admin.rs::routes()` registers only `POST /runner-fleets`, `GET /runner-fleets`, `POST /runners/enrollment`, `POST /runners/{id}/enrollment-tokens/{token_id}/revoke`, `POST /runners/{id}/revoke`, `POST`/`GET /agent-profiles`, `POST`/`GET /model-profiles` — no `GET` anywhere under `/runners`. The `agent_runners` table (migration 040, `crates/tack-db/src/migrations.rs`) already stores everything a health/capacity/protocol/harness display needs — `state`, `labels`, `total_capacity`, `available_capacity`, `capability_snapshot`, `protocol_version`, `last_heartbeat_at`, `revoked_at` — but nothing reads it back to the operator surface. This is the reason `EnrollmentPanel.tsx` can only show a session-local roster instead of a real one, and the reason `RunnerHealthCard.tsx`'s live call site never passes `connectionStatus: 'healthy'`: there is no heartbeat data to honestly justify it. `RunnerHealthCard.tsx` is fully built and tested against the real `RunnerCapabilities` shape, so wiring a future `GET /runners` response into it should need no further design work here — only a new list call plus a `stale`/`healthy` classification based on `last_heartbeat_at` age.
  2. **`agent_fleet_members` exists in the schema with no route.** Migration 041 creates the join table (`fleet_id`, `runner_id`) but `runner_admin.rs::routes()` has no endpoint that reads or writes it, and `FleetSummary`/`list_fleets` carries no roster count. `FleetsPanel.tsx` states this explicitly per row rather than building a membership editor with nothing to call.
  3. **No `enabled`/toggle endpoint for model profiles.** `list_model_profiles` returns `enabled: boolean` (defaulting `true` at creation, per the `model_profiles` table's own default) but `runner_admin.rs::routes()` has no route to flip it — `ModelProfilesPanel.tsx` only creates and lists, never disables.

  None of the three blocked this card's own deliverable — enrollment/revocation, fleet/profile create+list, and the capability-display component are all fully built and tested against the real, currently-shipped backend behavior, per this codebase's established precedent (`shared/execution/capabilities.ts`, `cache.ts` did the same for E2).

All three are the gaps requested above, not silent omissions — each is named in-product, not just in this document.
