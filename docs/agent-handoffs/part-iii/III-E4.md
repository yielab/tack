## A resolved contract ambiguity (per III.2 rule 13)

**The mismatch:** this card's acceptance bar says "an unsupported harness/provider/model combination cannot be submitted," but the only real data source for that judgment (`RunnerCapabilities[]`, via a `GET /runners`-style endpoint) does not exist anywhere in the operator API today — confirmed independently by re-reading `crates/tack-api/src/handlers/runner_admin.rs`'s `routes()` function (only `POST /runners/enrollment`, two `POST .../revoke` routes) and cross-checked against E2's own handoff (Gap 1) and E5's own handoff (the identical gap, found independently by a different card). Taken literally and strictly, "no capability data exists" would mean either (a) blocking every possible submission forever (a materially useless UI, since this whole card exists to let an operator start a run), or (b) silently reporting things as supported with no evidence (exactly what III.2 rule 7 forbids).

**The smallest decision:** split "a combination" into two real, distinct cases rather than treating "no data" as one universal answer. A **specific** model choice is a falsifiable technical claim ("this exact pair works") with nothing to back it today, so it stays hard-blocked, with the real reason, until a real endpoint exists. **Auto** (`requested_model_provider`/`requested_model_id` both `null`) is not a claim about a specific pair at all — III.1.2 defines it as an always-legal request shape precisely for when the operator has no strong preference — so it is never blocked by missing capability data; it gets an honestly-worded advisory instead, and the real enforcement remains the scheduler at claim time (III-E1's own acceptance line: "invalid combinations name reasons"). This is implemented, not just described, in `shared.ts#gateHarnessModelSelection`, and `shared.test.ts` proves both halves of the split with fixture `RunnerCapabilities` data (a genuinely-unsupported specific combination still blocks even with real data present; a cleanly-probed harness with Auto selected is allowed non-advisory) — so the "Auto never blocks" rule is demonstrated to be a real branch, not merely the accidental behavior of an always-empty capability list.

## Failure/adversarial case proved

- **A real harness-kind naming bug, caught before it shipped.** While grounding `HARNESS_KINDS`' wire values I found `crates/tack-cli/src/execution.rs`'s own unit tests use `"claude_code"` (underscore) as an example value for what is, on the wire, an untyped `String` — but the actual runner adapter (`crates/tack-runner/src/harness/claude_code.rs`)'s real `HARNESS_KIND` constant is `"claude-code"` (hyphen). Had I copied the CLI test's example string, Claude Code would have silently never matched any real runner's capability report (a byte-exact string compare in `isCombinationSupported`) — the picker would have looked correct but never worked. `shared.test.ts`'s first `HARNESS_KINDS` test pins the correct three values with the hyphen, and `shared.ts`'s own doc comment explains the discrepancy so a future editor doesn't "fix" it back to the wrong form.
- **The submit-gate split is proven load-bearing, not just permissive.** `shared.test.ts` and `RunWithAgentModal.test.tsx` both include a fixture `RunnerCapabilities[]` with a real harness/model combination, and assert a *different*, non-existent model id under the same harness is still blocked — proving the gate actually discriminates rather than being hardcoded to always-allow once any data exists.
- **Test-isolation bug in my own first E2E draft, caught by rerunning.** My first `run-with-agent.spec.ts`/`a11y.spec.ts` item-detail tests used the existing `getOrCreateItem` helper, which — as its own doc comment says — reuses the project's first existing item rather than guaranteeing a fresh one. Against this repo's persistent `e2e.db`, a second run of the same spec accumulated a second "Queued" execution on the same reused item, and a `getByText('Queued')` assertion that had passed on a clean db failed with a Playwright strict-mode "resolved to 2 elements" error on rerun. Fixed by adding `createFreshItem` (guaranteed new item id, mirroring `journey.spec.ts`/`table.spec.ts`'s existing direct-POST convention) and switching both specs to it; reran each spec twice in a row against the same `e2e.db` to confirm the fix holds under repetition, not just on a first, clean run.
- **`request_cancellation`'s known-inconsistent `state` field never leaks into this UI.** `ExecutionTimeline.tsx` renders cancellation status exclusively from `record.cancellation` (E2's derived state machine over `cancellation_requested_at`), never from a cancel response's own `state` string — the same discipline E2's handoff documents for exactly this reason (Gap 4).

## Schema/API/contract change requested from another owner

All three below are pre-existing gaps this card's UI runs into, already flagged by E2 and/or E5's handoffs — repeated here with this card's own concrete UI-shaped consequence, per III.2's "record the needed change in the handoff" rule. None were worked around by fabricating data; each has a typed, honest placeholder in the UI instead.

1. **No `GET /runners` (or per-fleet roster) endpoint** (E2 Gap 1, E5 Gap 1 — independently reconfirmed here). Consequence for this card: the "exact runner" target picker is a free-text id field with an explanatory hint, not a select; the harness/model submit gate can only ever show the "no runner capability data available" advisory for Auto selections and a hard block for every specific selection, since there is no live way to populate `RunnerCapabilities[]` from inside the running app. `RunWithAgentModal`'s `capabilities` prop is deliberately exposed (defaulting to `[]`) so this is a one-line wiring change, not a redesign, the moment the endpoint exists.
2. **`GET /executions/{id}` returns only 5 scalar columns** (E2 Gap 2). Consequence: `ExecutionTimeline`'s attempt sub-section is permanently the typed "not available yet" message; there is no route this card could call to render real attempt/event data even though it was asked for in the task list ("request/attempt timeline"). Requesting the same `GET /executions/{id}/attempts` route E5 already requested independently.
3. **No real "default" concept anywhere in the agent-profile/model-profile/fleet DTOs**, and III-F3 (the card that would define profile → project → fleet resolution precedence) is Wave 5, not yet landed. Consequence: "resolved default provenance" (this card's own task line) is implemented as a typed `not_available` placeholder end-to-end rather than a fabricated "first item wins" client convention — see "Behavior implemented" above. Requesting that III-F3 (or F4, "model provenance" per its own task list) close this by exposing an actual resolved-default endpoint/field, at which point `shared.ts#resolveDefaultProvenance` is the one function to update.
